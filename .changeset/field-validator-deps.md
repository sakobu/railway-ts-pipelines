---
'@railway-ts/use-form': minor
---

A field validator lists the fields it reads with the new `withDeps`, and its error lasts only while they hold the values it checked (#58). Validation asked for inside `onFieldChange` runs once, after the outermost call returns (#57). Every error the form shows now describes the values it holds.

**Breaking:** a function in `fieldValidators` gets only its value, and the `values` argument is gone. A validator that read other fields lists them with `withDeps(deps, validate)`, where `validate(value, depValues)` gets only the listed fields, or the rule moves into the schema with `refineAt`.

- New: `fieldValidators: { slug: withDeps(['workspaceId'], (slug, { workspaceId }) => …) }`. Each listed value comes in typed, and reading a field the validator didn't list is a type error. Write `withDeps` inside the `fieldValidators` entry, where it takes the form's types, or give its type arguments (`withDeps<Form, string, readonly ['workspaceId']>(…)`) to declare it elsewhere: one built for another form doesn't fit. Editing a listed field re-checks the validator in `live` mode, blurring one does in `blur` mode, and the next submit does in every mode.
- New type exports: `FieldValidatorWithDeps`, `DepValues`, `FieldValidatorAnswer` and `FieldTypeAtPath`, so a validator declared on its own can be typed, and exported from a package that emits declarations.
- **Breaking (types):** a validator's value, and each value `withDeps` lists, is typed `T | undefined` when an object on its path is optional or nullable: the form holds `undefined` there while that object is missing, and a submit, or an edit that clears the object, calls the validator with it. A tuple item's path is typed by index (`'pair.0' | 'pair.1'`), so a validator at a tuple item gets its item's type, and an index past the end no longer compiles.
- **One rule for every error:** an error shows only while the form holds the values it describes. An edit drops the schema and server errors at, inside or above each path whose value it changed, and each field-validator error whose field or listed field it changed, in every mode, and `isValid` follows. Clearing or removing an object, or removing an array item, counts as a change at its own path, so every schema and server error inside it goes. A Save button disabled while `!isValid`, and auto-save, no longer get stuck on an error for values the form no longer holds. Setting a field to an equal value keeps its errors, a server error included, which used to clear on any write to its field. A schema check that lands after an edit, and a failed save's `err` after an edit during the save, place their errors only where the values still match. So does `validateForm(values)` with values the form doesn't hold: the form shows only the errors at the paths where they match, and the result holds them all. **Breaking** in `blur`, `submit` and `mount` modes: typing in a field hides its schema error until the next check, where it used to stay until the next blur or submit. A whole-form schema error (path `[]`, as an object-level `refine` gives) describes every field, so any edit drops it: put a cross-field rule on its field with `refineAt` to keep it until that field changes.
- `setValues` that validates (by default in `live` mode, or with `shouldValidate: true` in any mode) runs the field validators of the values it changed.
- An edit re-checks a validator when a value it reads changed: editing `address.city` re-checks a validator on `address`, and setting `address` re-checks one on `address.city` when the city changed. An array helper re-checks the array's validator, not those of the items it left as they were. A key an edit adds or removes is a change, even one holding `undefined`. Setting a field to its own value still re-checks its validator and those of the objects around it.
- A schema error at, inside or above the validator's field or a listed field holds it back, so no request goes out with an input the schema rejects. A held-back check shows no error and no spinner, and runs once a schema check of the values the form holds accepts its inputs, whichever field the fix was in: fixing the email a rule on `username` reads runs the `username` lookup. **Breaking** for a validator on an object field: it no longer runs while a schema error sits inside that object. **Breaking** too: a root schema error sits above every field, so it holds back every validator until it clears: put a cross-field rule on its field with `refineAt` to keep the other lookups running.
- A field check of values the form no longer holds ends with no error, such as a submit's check of a field edited while the submit's schema check ran. `handleSubmit`'s `err` still includes it.
- A submit whose schema or field checks fail on values the form no longer holds when it returns (after an edit, a follow of new `initialValues` or `resetForm()`) now says so: the submit error reads "The values changed while they were checked, so nothing was saved. Review them and save again.", and `err` holds it at path `[]` after the errors. A blur's re-check of unchanged values that answers differently doesn't count. The new `messages.changedWhileChecking` replaces the text. Not while auto-save can save the changed values on its own: with auto-save on and the form not stale.
- A `withDeps` validator's error shows through `getFieldError` once its field or a field it lists is touched, so picking another workspace shows that the slug is taken there. Only `getFieldError` and the array helpers' `getFieldError` apply this rule, since `touched` is unchanged: a form that renders `touched.slug && errors.slug` itself still hides the error until the slug is touched.
- The array helpers' `getFieldError(index, subField)` shows an error by the same rules as `form.getFieldError`, so a group error at an item's path also shows once a field inside it is touched, where it used to need a touch at that exact path.
- A follow of new `initialValues` changes the values as an edit does. In `live` mode it re-runs each field validator whose field or listed field it changed, even one that passed, so a refetch can send lookups: a check like "username taken" that should accept the record's own value lists the record's id with `withDeps`. In every mode, a check the follow cut short runs again while its values hold. A follow that only server errors preceded now re-validates too, as one that other errors preceded does. **Breaking:** a follow no longer re-runs a validator only because it showed an error. One whose values the follow left as they were keeps its error, and outside `live` mode one whose values it changed loses its error and waits for the next blur or submit.
- `shouldValidate: true` on an edit that makes the form follow new `initialValues` now checks the edit's fields too, along with the follow's own checks.
- `setFieldTouched(field, true, true)` now checks the schema and the field validators the field reaches in every mode. In `live` mode it used to check only the schema on a first touch, and nothing after. Left out, `shouldValidate` still lets the mode decide, and `false` never checks.
- Validation asked for inside `onFieldChange` runs once, after the outermost call returns. A cascade no longer runs a validator twice, and the schema runs once per call.
- A sync throw from a check asked for inside `onFieldChange` reaches the outermost call, and so does one from a check that the call's schema check releases or moves on. A sync throw from the schema in `resetForm()` (in `mount` mode), or from the schema or a field validator in a follow an edit caused, reaches the caller instead of being logged. An event with no caller that starts inside a call, such as a `resetKey` reset committed with `flushSync` in `onFieldChange`, runs as its own once that call has returned, and logs its throws.

Fixes #58, Fixes #57
